## 프로젝트 목표

고객 문의 티켓을 받아 **유형을 분류**하고, 사내 정책·주문 정보를 근거로 **답변 초안을 생성**해 상담원에게 제시하는 서비스입니다.

이 프로젝트는 세 가지를 증명하는 것을 목표로 합니다.

| # | 증명하려는 것 | 방법 |
|---|---|---|
| 1 | **아키텍처 일반화** | 선행 프로젝트([분필](https://github.com/MachuEngine/bunpil), 교육 도메인)에서 검증한 LangGraph ReAct + RAG + 가드레일 + eval 구조가 전혀 다른 산업 도메인에서도 성립하는지 |
| 2 | **벤더 통합 깊이** | 공식 LangChain 통합(`ChatAnthropic`)과 `BaseChatModel`을 직접 상속한 커스텀 어댑터를 **둘 다** 구현하고, 언제 어느 쪽이 필요한지 판단 기준을 문서화 |
| 3 | **개발 과정의 하네스 설계** | 에이전트 제품에 가드레일을 넣는 것과, 에이전트로 개발하는 과정에 가드레일을 넣는 것은 같은 문제라는 관점을 실제 훅·루프로 구현 |

> **자동 응답이 아니라 상담원 증강(human-in-the-loop)입니다.** 모든 출력은 상담원 검토 대상이며, 확신도가 낮으면 초안을 만들지 않고 사람에게 넘깁니다.

### 도메인을 "얇게" 특화한 이유

특정 버티컬로 좁게 못 박지 않았습니다. 좁히면 (a) 도메인 실무 지식 부족으로 평가 신뢰도가 떨어지고, (b) 포트폴리오 평가 축이 "도메인 지식"으로 오해됩니다. 실제 축은 **에이전트·RAG·가드레일·평가 설계 역량**입니다.

대신 tool·정책·평가를 **구체적으로 정의할 수 있을 만큼만** 좁혔습니다 — 이커머스는 주문조회·반품·배송 tool이 직관적이고, 정책 위반의 정의가 명확하며, 직접 검증이 가능합니다.

사용하는 [Bitext 데이터셋](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset)은 스스로를 "customer service **verticalization**용"으로 규정하며, 특정 산업에 종속되지 않는 공통 인텐트 27개만 담고 있습니다. 이 "범용 베이스 → 도메인 특화" 2단계 설계를 그대로 프로젝트 구조로 차용했습니다.

1. 공통 인텐트로 CS 에이전트 **기본 동작** 구현
2. 그 위에 **얇은 이커머스 특화 레이어**(합성 정책 문서 + 도메인 tool + 도메인 평가)를 얹기

→ "이커머스 CS를 만들었다"가 아니라 **"범용 CS 파이프라인을 도메인에 특화시키는 과정을 재현했다"**.

### 언어 정책

**파이프라인은 영어, 프로젝트 문서는 한국어입니다.** 티켓·정책 문서·프롬프트·생성 초안·PII 패턴은 전부 영어이고, 설계 문서·커밋 메시지·UI 레이블은 한국어입니다.

Bitext 데이터셋이 **영어 전용**이기 때문입니다. 인텐트 라벨이 이 프로젝트의 유일한 외부 ground truth인데, 번역을 끼우면 정확도가 떨어졌을 때 원인이 모델인지 번역인지 분리할 수 없게 됩니다. 정책 문서까지 영어로 통일하면 RAG 질의와 코퍼스가 같은 언어라 검색도 자연스럽습니다.

## 아키텍처

```
티켓 입력 → PII 마스킹 → [모듈 ①] Triage (인텐트 · 카테고리 · confidence)
                              │
                    confidence < 임계 ─→ escalate (초안 없음, 사유만)
                              │
                              ▼
                   [모듈 ②] ReAct Agent ↔ tools (주문 / 정책 / 등급)
                              │ submit_for_review
                              ▼
                   judge_node  (별도 벤더 LLM: 정책 준수 + 톤 채점)
                              │
                              ▼
                   validate_node  (코드: threshold · 근거 인용 · PII 판정)
                              │
                 ┌────────────┼────────────┐
              통과          미달·budget>0   미달·budget=0
                 │              │              │
                 ▼              ▼              ▼
          상담원 검토 초안    agent 재시도    escalate (사람)
```

| 모듈 | 입력 | 처리 | 출력 |
|---|---|---|---|
| 🏷️ **티켓 분류** | 티켓 본문 | 단일 LLM 호출 + 구조화 출력 (에이전트 아님) | 인텐트 · 카테고리 · confidence |
| ✍️ **답변 초안** | 티켓 + 분류 결과 | ReAct 에이전트가 정책 RAG·주문 DB를 참조하며 초안 작성 → **별도 벤더 Judge**가 정책 준수·톤 채점 → 코드가 통과 판정 → 미달 시 재시도 | 초안 + 인용 정책 조항 + 사용 도구, **또는** 에스컬레이션 사유 |

### 도구 (Tools)

모든 도구는 **LLM 호출 없이 순수 계산·검색·저장만** 수행합니다. 추론과 문장 작성은 에이전트가 직접 담당합니다 — 도구 안에 LLM을 중첩하는 안티패턴을 배제했습니다.

| 도구 | 역할 |
|---|---|
| `search_policy` | 반품·교환·환불·배송 정책 조항 검색 (ChromaDB + Rerank) |
| `lookup_order` | 주문 상태·배송 추적 조회 (합성 DB) |
| `check_customer_tier` | 고객 등급 조회 (등급별 정책 분기용) |
| `validate_draft_format` | 초안 형식 검증 (결정론적) |
| `save_draft` | **게이트 4종 통과 시에만** 저장 |
| `discard_draft` | 초안 폐기 (교체 시) |
| `escalate_to_human` | 스스로 처리 불가 판단 시 명시적 신호 |
| `submit_for_review` | 작성 완료 신호 |

**`save_draft`의 결정론적 게이트** — 거부 시 사유를 도구 응답으로 되돌려 에이전트가 스스로 교정하게 합니다.

1. **PII 재유출** — 마스킹 토큰이 복원됐거나 새 PII가 초안에 들어갔는가
2. **근거 없는 확약** — 도구 결과에 없는 금액·날짜·환불 확약이 포함됐는가
3. **금지 표현** — 법적 확약, 타사 비방, 과장 (규칙 기반)
4. **정책 인용 존재** — 정책 판단이 필요한 인텐트인데 인용된 조항이 0건인가

### 세 가지 종료 상태

선행 프로젝트는 "통과 / 예산 소진" 2상태였지만, CS는 **에스컬레이션을 1급 종료 상태**로 뒀습니다. 실제 프로덕션 CS 패턴(컨피던스 임계값 라우팅)과 일치합니다.

| 상태 | 조건 | 상담원이 보는 것 |
|---|---|---|
| `auto_draft` | 에스컬레이션 조건 미해당 & Judge 통과 & 코드 검증 통과 | 초안 + 인용 정책 + 사용 도구 |
| `escalated` | 아래 8개 조건 중 하나라도 해당 | **초안 없음** + 사유 |
| `failed` | 파이프라인 예외 | 오류 표시 (내부 상세 비노출) |

**에스컬레이션 조건 8종** — 판정은 전부 **코드**가 합니다.

| | 조건 | | 조건 |
|---|---|---|---|
| E1 | 분류 confidence < 임계값 | E5 | 에이전트가 `escalate_to_human` 호출 |
| E2 | `contact_human_agent` (고객이 사람을 명시 요청) | E6 | 주문 조회 실패 |
| E3 | `complaint` (보상·책임 판단이 섞임) | E7 | `save_draft` 게이트 3회 연속 실패 |
| E4 | `flags`에 `W`(공격적 표현) 포함 | E8 | 재시도 예산 소진 |

> **초안이 없는 것이 잘못된 초안보다 낫습니다.** 예산 소진 시 마지막 미달 초안을 그냥 내보내지 않습니다.
>
> E3(불만)을 자동 초안에서 뺀 이유: 보상 여부·금액 판단이 섞이는데 이건 정책 문서만으로 결정되지 않는 **제품 판단**입니다. 초깃값으로 전량 에스컬레이션하고, FP율이 과하면 그때 세분화합니다.

## 설계 원칙

### 1. LLM이 판단하고, 코드가 결정한다

| 검증 대상 | 판단 주체 | 근거 |
|---|---|---|
| 정책 준수 · 톤 적절성 | **별도 벤더 Judge LLM** → threshold는 코드 | 정성 판단은 LLM이 낫고, 커트라인은 코드가 안정적 |
| 사람 개입 필요 여부 | LLM이 confidence 기록 → **코드가 임계값 비교** | 라우팅 결정을 LLM에 맡기면 제어가 깨짐 |
| PII 재유출 · 근거 없는 확약 | **코드** (`save_draft` 게이트) | 안전 검사는 확률적 판단에 맡기지 않음 |
| 재시도 · 에스컬레이션 여부 | **코드** (budget 루프) | — |

### 2. Judge는 도구가 아니라 별도 노드이며, 생성과 다른 벤더를 쓴다

선행 프로젝트에서 얻은 교훈입니다. 처음에는 생성 에이전트가 도구로 **자기 출력을 스스로 채점**했는데, 그 신뢰도는 사람 라벨과 한 번도 대조된 적이 없었고, 정작 오프라인 평가가 검증하는 Judge와 런타임에 배포된 Judge가 **서로 다른 코드 경로**였습니다(검증-배포 불일치).

이 프로젝트는 **처음부터** `judge_node`가 오프라인 평가와 **동일한 함수**를 호출하도록 설계했습니다. 그래야 평가 기록의 Judge 신뢰도 수치가 곧 배포된 Judge의 신뢰도입니다. 정책 위반·톤은 주관성이 더 강해 이 분리가 특히 중요합니다.

또한 Judge는 생성 모델과 **다른 벤더**를 씁니다 — "생성 모델이 자기 글을 자기가 채점하지 않는다"의 가장 강한 형태입니다.

### 3. 보안 하드룰 (예외 없음)

실제 고객 데이터 미사용(공개 데이터셋 + 합성) · **PII 마스킹은 모델 호출 이전** · 티켓 본문 비저장 · 로그·캐시에 PII 금지 · 근거 없는 확약 금지 · 서버 간 API 키 인증 · 출력에 **"상담원 최종 책임(보조수단)" 고지**.

CS 도메인에는 교육 도메인에 없던 문제가 하나 있습니다 — **모든 식별자를 마스킹하면 도구가 동작하지 않습니다.**

| 구분 | 대상 | 처리 |
|---|---|---|
| **마스킹** | 이메일 · 전화번호 · 카드번호 · 주소 · 인명 | `{{EMAIL}}` 등으로 치환 |
| **유지** | 주문번호 · 송장번호 · 고객ID | 그대로 — `lookup_order`의 입력 |

초안에 마스킹 토큰이 남는 것은 정상이며, 상담원이 검토 단계에서 복원합니다("상담원 최종 책임" 원칙과 일관).

### 4. 평가 기반 개발

골든셋은 코드에 하드코딩하지 않고 전부 외부 파일로 관리하며, **정답셋과 평가 실행 코드는 개발 에이전트가 수정할 수 없도록 훅으로 차단**합니다.

## 평가 설계

**원칙**: ① LLM Judge는 사람 라벨과 먼저 일치율을 검증한다 ② 정량(함수)/정성(Judge·사람)을 분리한다 ③ 골든셋은 외부화한다.

### 티켓 분류

| 지표 | 판정 | 목표(시작값) |
|---|---|---|
| 인텐트 정확도 (27-class) | 함수 (Bitext 라벨) | ≥ 0.85 |
| 인텐트 macro-F1 | 함수 | ≥ 0.80 |
| 카테고리 정확도 (11-class) | 함수 | ≥ 0.92 |
| confidence 캘리브레이션 | 함수 | 오분류 건의 confidence가 유의하게 낮은가 |

> **macro-F1을 함께 보는 이유**: Bitext는 인텐트당 약 1,000건으로 **분포가 균등**하므로 불균형 보정 목적이 아닙니다. 목적은 **인접 인텐트 쌍의 국소적 붕괴 탐지**입니다 — `check_invoice`↔`get_invoice`처럼 의미가 붙어 있는 쌍은 한쪽이 무너져도 전체 accuracy가 거의 움직이지 않습니다. 혼동행렬을 함께 리포트합니다.

### 답변 초안

| 우선 | 지표 | 판정 | 목표(시작값) |
|---|---|---|---|
| 🔴 | PII 마스킹 누락률(FN) | 함수 | **0** |
| 🔴 | 정책 위반 검출 Recall | 함수 | ≥ 0.95 |
| 🔴 | 근거 없는 확약률 | 함수 | **0** |
| 🟡 | 톤 적절성 | LLM Judge | 5점 평균 ≥ 4.0 |
| 🟡 | **Judge 신뢰도 (Cohen's κ)** | 사람 라벨 대비 | ≥ 0.4 |
| 🟢 | 정책 RAG Recall@5 | 함수 | ≥ 0.8 |
| ⭐ | **에스컬레이션 Recall** | 함수 | ≥ 0.9 |
| ⭐ | 에스컬레이션 FP율 | 함수 | 참고값 (트레이드오프는 사람 판단) |
| 🏁 | 상담원 무수정 채택률 | 사람 | 북극성 |

**에스컬레이션 Recall이 이 프로젝트 고유 지표입니다.** "사람이 개입해야 했던 케이스를 실제로 넘겼는가". 넘겼어야 하는데 자동 초안을 낸 것(FN)이 과잉 에스컬레이션(FP)보다 훨씬 위험하므로, Recall만 게이트로 두고 FP율은 참고값으로 관리합니다.

**Judge 신뢰도를 가장 먼저 측정합니다.** κ가 목표에 미달하면 그 Judge 점수로 통과/재시도를 결정하지 않습니다 — 못 믿을 Judge 위에 다른 수치를 쌓으면 전부 다시 해야 합니다.

> ⚠️ **선행 프로젝트에서 겪은 함정**: "평가가 존재하는가"와 "내 변경이 평가가 실제로 exercise하는 경로에 있는가"는 별개입니다. 생성 프롬프트를 개선했는데 수치가 전혀 변하지 않은 적이 있었고, 원인은 평가가 하드코딩된 고정 출력을 채점하는 구조였기 때문입니다. 이 프로젝트의 평가는 **실제로 파이프라인을 돌려 새 초안을 생성한 뒤 채점**하도록 설계했습니다.

## 벤더 연동 전략

공식 통합과 커스텀 어댑터를 **둘 다** 구현하고, 판단 기준을 `VENDOR_INTEGRATION.md`로 남깁니다.

| 기준 | 정식 지원으로 충분 | 커스텀 어댑터 필요 |
|---|---|---|
| LangChain 공식 패키지 | 있음 (`langchain-anthropic`, `langchain-openai`, `langchain-aws`) | 없거나 표준과 다름 |
| API 계약 | 단일 **동기** 요청-응답 | **비동기 job queue** (제출 → job id → 상태 폴링) |
| 예시 | Anthropic API, OpenAI, Bedrock, SageMaker Serverless | RunPod Serverless (자체 job queue) |

**근거**: 선행 프로젝트의 RunPod 어댑터를 검토한 결과, RunPod serverless는 비동기 job queue 프로토콜을 쓰기 때문에 `BaseChatModel`을 직접 상속하는 커스텀 어댑터가 **실제로 필요했던** 케이스였습니다. GPU 서버리스 특성(긴 콜드스타트, 워커 오토스케일링 큐잉)상 구조적으로 비동기가 자연스럽습니다. 반면 Bedrock(`InvokeModel`/`Converse`)과 SageMaker Serverless Inference는 동기 요청-응답이라 공식 클래스로 충분합니다.

**커스텀 어댑터가 실제로 구현해야 하는 것** — `_generate`/`_agenerate`, `bind_tools`(LangChain 도구 → OpenAI 호환 schema 변환), 메시지 양방향 변환(role 매핑·`tool_calls` 구조·`tool_call_id`), 그리고 **동일 job_id 폴링**(제출 응답을 못 받았다고 재제출하면 중복 실행).

→ "라이브러리를 갖다 쓸 줄 안다"를 넘어 **"LangChain 내부 구조를 이해하고 확장할 수 있다"**를 증명하는 것이 목적입니다.

파이프라인 코드는 벤더 클래스를 직접 import 하지 않고 항상 추상화 레이어를 경유합니다 — 이 규칙이 깨지면 벤더 전환 실험 자체가 불가능해집니다.

## 개발 하네스 · 루프 엔지니어링

> **에이전트 제품에 가드레일을 넣는 것과, 에이전트로 개발하는 과정에 가드레일을 넣는 것은 같은 문제입니다.** 둘 다 모델의 협조에 의존하지 않는 시스템 레벨 강제가 필요합니다.

이 레포는 Claude Code로 개발하는 과정 자체를 하네스(무엇을 할 수 있는가)와 루프(어떻게 반복하는가)로 설계합니다.

**핵심 원칙: 평가의 정답셋과 평가 실행 코드는 개발 에이전트가 수정할 수 없어야 한다.**

| 층 | 수단 | 성격 |
|---|---|---|
| Layer 1 | `CLAUDE.md` | 판단 기준 — 모델의 협조에 의존 |
| Layer 2 | `.claude/settings.json` `permissions.deny` | 선언적 1차 방어 |
| Layer 3 | `.claude/hooks/*.py` (PreToolUse) | 우회 경로까지 차단하는 2차 방어 (exit 2) |

훅은 **Python(stdlib만)**으로 작성합니다 — jq 외부 의존성 없이 이식 가능하고, 프로젝트 언어와 일치해 테스트를 붙이기 쉽습니다.

**차단 대상**: 보호 경로(`evals/golden/`, `evals/runners/`, `data/raw/`) 쓰기 · API 키 패턴 · `.env` 열람/전송 · 전체 평가(`--full`) 무단 실행.

**루프 3종**

| 루프 | 종료 조건 | 최대 시도 | 에스컬레이션 |
|---|---|---|---|
| A. 기능 구현 | 테스트 통과 | 3 | 세 번의 가정과 오류를 요약 후 중단 |
| B. RAG 품질 | Recall@5 ≥ 목표 | 2 | 청킹 전략 선택지 제시 후 사람 결정 |
| C. 가드레일 | 위반 F1 ≥ 목표 & 톤 ≥ 임계 | 2 | **반드시 사람 리뷰** |

루프 C는 **자동 종료를 만들지 않습니다.** 정책 위반 검출의 FP/FN 균형은 제품 판단이지 기술 판단이 아닙니다 — 제품 쪽 HITL 설계와 같은 논리를 개발 워크플로우에도 적용했습니다.

> **종료 조건보다 포기 조건 설계가 어렵고 더 중요합니다.** 3회 실패 시 멈추고 "무엇을 가정했고 무엇이 틀렸는지"를 보고하게 합니다. 같은 실패 패턴이 3회 기록되면 훅으로 승격시킵니다 — "기억하기"에서 "실행 불가능하게 만들기"로.

## 기술 스택

| 구분 | 선택 |
|---|---|
| 백엔드 | FastAPI (비동기) |

| 프론트엔드 | Next.js (상담원 검토 UI) |
| 관측·평가 | LangSmith · Ragas |
| 배포 | Docker + Caddy HTTPS (클라우드 VM) |

## 데이터

### Bitext 데이터셋 (실측 검증 — 2026-07-28)

| 항목 | 확인된 값 |
|---|---|
| 규모 | 26,872 QA 쌍 (인텐트당 약 1,000건 — 분포 균등) |
| 인텐트 / 카테고리 | **27개 / 11개** (`ACCOUNT` `CANCEL` `CONTACT` `DELIVERY` `FEEDBACK` `INVOICE` `ORDER` `PAYMENT` `REFUND` `SHIPPING` `SUBSCRIPTION`) |
| 컬럼 | `flags` · `instruction` · `category` · `intent` · `response` |
| 언어 | **영어 전용** |
| 라이선스 | **CDLA-Sharing-1.0** (share-alike) |
| 엔티티 | `{{Order Number}}` 형식 플레이스홀더 약 30종 |

`flags`는 언어 생성 태그(정중·구어·오타·공격적 표현 등)로, 파이프라인이 실제로 사용합니다 — **`W`(공격적 표현)는 에스컬레이션 조건**으로, `P`/`Q`/`Z`는 톤·강건성 평가의 층화 샘플링 축으로 씁니다.

> ⚠️ **`response` 컬럼은 정답셋으로 쓰지 않습니다.** 플레이스홀더가 박힌 범용 템플릿이고 우리가 합성할 정책 문서에 근거하지 않기 때문입니다. 이걸로 채점하면 "우리 정책에 맞는 답"이 아니라 "Bitext 템플릿과 비슷한 답"을 평가하게 됩니다. 영어 CS 문체 참고용으로만 씁니다.

> ⚠️ **플레이스홀더는 실제 값이 아닙니다.** `{{Order Number}}`는 문자열 리터럴이라 그대로 두면 `lookup_order`가 조회할 대상이 없습니다. 합성 DB를 먼저 만들고 그 값을 주입하는 **하이드레이션 단계**를 거칩니다. 이때 약 10%는 의도적으로 존재하지 않는 주문번호로 채워, 에스컬레이션 경로가 실제로 발생하도록 합니다.

### 합성 데이터

| 항목 | 내용 | 용도 |
|---|---|---|
| 정책 문서 | 가상 이커머스사 영문 규정, **조항 번호 부여**(`RET-03` 등), 등급·기한 분기 포함 | 정책 RAG 코퍼스 · 인용 근거 |
| 주문·고객 DB | SQLite (`orders` / `customers`, tier 3종) | `lookup_order` · `check_customer_tier` |
| 골든셋 6종 | 분류 200 · **PII 50** · 정책위반 50 · 톤 30 · 에스컬레이션 40 · 검색 30 | 평가 |

> **PII 골든셋이 따로 필요한 이유**: Bitext는 이미 익명화돼 있어 **마스킹할 실제 PII가 없습니다.** 🔴 안전 지표인 마스킹 누락률을 측정하려면 PII를 주입한 테스트셋이 반드시 있어야 합니다.

**⛔ 절대 금지**: 실제 고객 문의, 실제 주문 정보, 식별 가능한 개인정보 수집. `data/raw/`는 커밋하지 않고 다운로드 스크립트로 재현합니다(CDLA-Sharing-1.0 재배포 조건 회피 + 레포 경량화).
